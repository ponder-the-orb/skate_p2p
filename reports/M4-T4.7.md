  - The write queue starts as `null`, deliberately NOT a completed `Future.value()` sentinel. A future carries its creation zone; a sentinel built in a test's `setUp` sits in a zone whose microtasks the widget-test body never drains, which silently hung the very first `load()`. Cost me the afternoon; worth the comment that is now in the file.
  - TOUCH FIRES ON *APPLIED* EVENTS ONLY, per the ticket's word. An opcode the engine rejects (a TRICK_SET from the defender, say) does not refresh the save. Arguable either way — a rejected packet is still evidence the game is live — but "applied" is what the ruling said, and the 180 s window makes the difference unreachable in practice.
  - THE SAVE IS NOT CLEARED ON PEER_LEFT, CANCEL OR LEAVE-MATCH. The ticket named exactly three hooks and those are not among them, so I did not add a fourth. Consequence: after a peer leaves, a stale save can still show a Rejoin button for up to 180 s; tapping it takes the room-not-found path, which shows the friendly copy and clears it. Self-healing, one wasted tap. If you want it tidier that is a two-line follow-up.
  - A FAILED REJOIN TAP LEAVES THE BUTTON ON SCREEN. `load()` happens once in `initState`, as ruled, so the lobby does not re-read after the error. Tapping again is harmless and idempotent — and I kept it that way on purpose, because hiding the button on the first failure would also hide it when the failure was a dropped socket rather than a dead room.
  - ROOM FULL (`0x01`) AFTER A REJOIN TAP DOES NOT CLEAR THE SAVE — only `0x02` does, which is what the ticket says. Pinned as a test. It is the right call anyway: `0x01` means the room is alive.
  - THE PENDING FLAG IS CLEARED BY *ANY* ERROR, NOT ONLY `0x02`, as ruled. So a `0x01` followed later by a `0x02` reads as a manual failure and keeps the save. Also pinned as a test.
